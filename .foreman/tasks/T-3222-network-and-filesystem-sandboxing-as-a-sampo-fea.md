# Network and filesystem sandboxing as a Sampo feature: one sampo sandbox verb that turns…
## Raw request
> Network and filesystem sandboxing as a Sampo feature: one sampo sandbox verb that turns on Claude Code's built-in sandbox (bwrap) for session Bash commands with a network allowlist learned from the ledger (github ssh 443, pypi, the Jarvis endpoint), and extends Sampo's own Landlock confinement (fm code, calling cards, local-model runs) with kernel read-deny on credential folders and ABI 4+ TCP port rules; doctor check; nothing a user has may break (user ask 2026-11-05: would this be a possible feature we could add to sampo? network and filesystem sandboxing)
## Interpretation
The user asked (2026-11-05) whether Sampo could add network and filesystem sandboxing, then 'and maybe container isolation as a thing too?'. Read: Sampo should confine what runs on the user's machine at the kernel level, not only by Ward reading command text: every job Sampo starts (tests, fm code workers, calling cards, local-model tool runs, ship's scratch tests) and the session's own Bash commands, with (a) writes only where the job's work is, (b) no reads of credential folders, (c) network off or limited to an allowlist, (d) a container tier: each job in its own namespaces with a throwaway root. Constraints: nothing installed (bwrap 0.13, socat, unshare, docker 29 and Landlock ABI 10 are already here), nothing a user already has may break (git push over ssh.github.com:443, the Jarvis endpoint, Ollama on loopback), works in the Claude Code plugin too.

## Acceptance criteria
- [x] sampo sandbox run confines a job: a write outside its project and scratch, a read of ~/.ssh or ~/.config/sampo/secrets.env, any connection with --net off, a non-allowed host or 169.254.169.254 with --net allow, and a signal to a process outside all fail, while git, python tests, an allowed host and loopback Ollama when allowed work unchanged — verify with `python3 plugin/tests/run.py test_sandbox`
- [x] Network and filesystem sandboxing as one sampo sandbox verb: status names each layer (session, job, Landlock, docker) and whether it is live; on writes Claude Code's sandbox settings with a backup, credential folders read-denied and ssh-based git excluded; off restores the file byte for byte — verify with `python3 plugin/tests/run.py test_sandbox`
- [x] Container isolation: each sandboxed job gets its own user, mount, pid, ipc and uts namespaces and a throwaway root with only the project and scratch writable; --image runs it in docker instead, never by default — verify with `python3 plugin/tests/run.py test_sandbox`
- [x] nothing a user has may break: without bwrap or user namespaces every job runs as today and doctor says why; git push over ssh.github.com:443, the Jarvis endpoint and loopback Ollama keep working with the session sandbox on — verify with `python3 plugin/tests/run.py test_sandbox test_doctor`
- [x] the test runner can run every class sandboxed (run.py --sandbox) with the suite green and its overhead measured in research/sandbox.md — verify with `python3 plugin/tests/run.py --sandbox test_sandbox test_models && test -s research/sandbox.md`
## Non-goals
No new software installed. No sandbox for hooks themselves (Claude Code runs them with full access; Ward stays their guard). Ward trusting the sandbox is a separate security task after this lands.
## Approach (options → choice → why)
1) Claude Code's sandbox only (a settings writer plus an allowlist): fails if: Sampo's own jobs and every hook run outside Claude Code's Bash (hooks are never sandboxed), and in bypass mode an unlisted host is allowed unless strict.
2) Sampo's bwrap runner for everything, rewriting each session command in PreToolUse: fails if: rewriting breaks interactive tools, duplicates Claude Code's own sandbox, and one hook bug blocks every command.
3) Landlock only (credential reads denied by allow-list inversion, ABI 4 TCP port rules): fails if: ports are not hosts, nothing isolates pids or mounts, and the user asked for container isolation too.
4) Docker per job: fails if: the docker group is root-equivalent, starts cost seconds per test class, and most users' machines lack it.
5) Layered: Claude Code's sandbox for the session, a bwrap container tier for Sampo's jobs with a filtering proxy for allowlists, Landlock inside, docker only on request: likely outcome: every job and command confined by tools already installed, each layer falling back to today's behaviour when its tool is missing.
6) do less: document Claude Code's sandbox setting, no verb: fails if: Sampo's tests, workers and hooks stay unconfined and nothing learns or proves the allowlist.
Choice 5 (75%): each layer covers what the others can't (hooks and Sampo's jobs vs the session's Bash; hosts vs ports; namespaces vs Landlock), all from bwrap, socat, unshare and Landlock already here.
Build vs reuse: reuse infra.sandbox_prefix's unshare probe, oracle.py's bwrap argv, landlock.prepare and prepare_jail, callcards' jail and works' ENV_KEEP; Claude Code's sandbox for the session rather than a command rewriter of our own; no new dependency.
## Risks and rollback
Unprivileged user namespaces off on a user's distro: sandbox.available() says why and every job runs as today (a doctor line, never a failure). A job that needs the network or a home file fails inside: the runner names the denial (path or host) and the job declares the need. Claude Code's sandbox breaks ssh git push: excludedCommands covers git push and sampo ship, tested. Proxy misfilters: allowlist mode is opt-in; off and on stay the defaults. Overhead per job measured before test runs default to it. Rollback: sampo sandbox off restores settings.json from its backup byte for byte; each layer is behind its own switch; reverting the verb's commits leaves every caller on today's path.
Blast radius (sampo graph blast): unknown, no co-change history for research/sandbox.md.
