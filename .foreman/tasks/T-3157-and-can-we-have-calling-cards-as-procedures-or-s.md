# Calling cards: verified generators any model calls by name with typed inputs; the card's generator and checker do the work, so even a small local model gets correct code, SVG, docs, configs or operations without writing code or reasoning at length
## Raw request
> and can we have calling cards as procedures or something? this would be a new AI concept, but so models don't need to write code/whatever manually, so even smaller models like the local ones can still do things, you might need Opus to help write this and such, but it would genuinely massively increase capability, and make it super efficeint, effective, and no token burn on reasoning/whatever, they just do it directly
## Interpretation
Reading 1 (chosen): a new card kind, the calling card: name, purpose, a JSON-schema input, an output kind (file edit, new file, SVG, doc, config, command, data), a generator (py: a pure function run under the guard; template: typed slots; model: one constrained model step with a JSON schema or grammar, best-of-N until the checker passes; chain: other cards in order, outputs wired to inputs), a checker the output must pass (tests, lint, schema, render gate), preconditions, examples and provenance with pass stats. Callers (fm code's tools, sampo card call, MCP) pass inputs; Sampo runs generator then checker and returns verified output or a typed failure, never unchecked output. Opus writes the cards from mined repeats, fixes and ledger tool-call sequences; a card is admitted only when its tests pass; a small model's 'no card fits' files a card request. Reading 2: parameterised shell procedures only (the first message); rejected by the user's follow-up: cards must generate artifacts, generically, beyond code.

## Non-goals
## Approach (options → choice → why)
1) Use what exists: smallcards' store and admit() for the record, mcp.py's (schema, argv) registry pattern for typed calls, fm edit batches for file output, Ward plus Landlock for running, Smith's TOOLS and JSON-action path for the call; likely outcome: callable cards inside today's safety. fails if: smallcards' 3-12 literal steps can't hold code and schemas (then a sibling store, same admit style). 2) Do less: playbooks with typed slots a small model fills; fails if: no checker, so mistakes pass. 3) A card DSL compiled to Python; fails if: models must learn a new language and every card needs a compiler path. 4) Code-as-action (the small model writes Python that calls card functions); fails if: it brings back code writing by the small model; kept only for Opus-written chain cards. Choice 1 (75%): the safety, store and call paths exist; the new parts are the generator kinds, the checker run and the retrieval.
## Risks and rollback
Risks: a py generator is code Sampo runs: every run goes through Ward and Landlock with the worker env stripped of credentials, never as the user's shell; inputs are schema-checked and a template slot never reaches a shell unquoted. A checker that passes wrong output is the real failure: each card carries tests that include a known-bad input its checker must reject. Cards that rot as the code moves: the call stats and a nightly card test run retire failing cards. Small models picking the wrong card: retrieval returns top-k with purposes, and a call's checker failure is a typed result, not output. Rollback: the store is a new folder and the call tool is additive; removing the tool from Smith's list turns it off.

- **Opus-authored cards with a promotion gate:** add `fm card compile` that takes a `fm replay` trace, has Opus draft a parameterized card, dry-runs it against `plugin/tests/fixtures/`, and only then writes it into `plugin/cards/`. Registered in `fmguard.py` so unvetted cards can't run.
- **Retrieval-first router:** a small matcher (keywords or embeddings over card descriptions) selects the top-k cards for a task and injects only those into the local model's prompt, keeping the context small. This is complementary to the runner, not a replacement.
Failure modes:
- **Collision with existing "cards":** if `plugin/cards/` and its consumers already mean something different (docs, UI cards, or the `fmambient` and `fmanergy` flows), a new procedure format forks the concept. Check the existing schema and its tests in `plugin/tests/` before introducing fields.
- **Unsafe execution path:** a runner that executes card steps bypasses `plugin/lib/fmguard.py` permission checks, so a small model can trigger destructive steps through a card. Cards must route every step through the same guard and hook pipeline.
- **Brittle parameter binding:** local models pass malformed or hallucinated args (wrong types, missing fields, nonexistent card names). Without strict schema validation and clear error returns, the "no reasoning needed" promise collapses into retry loops that burn more tokens.
- **Card drift and untested procedures:** Opus-written cards go stale when the repo changes (`fmcore.py` and `fmcli.py` are the most changed files), and nothing catches it. `fm doctor` and `plugin/tests/run.py` need a check that every card still dry-runs, or cards silently break.
