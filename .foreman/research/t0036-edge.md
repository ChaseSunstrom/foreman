Confirmed: no test exercises content_hash returning None at grant time, the unlocked-check-then-locked-consume race, or malformed/non-list `plugin_pin` values. This corroborates the findings below.

## Verdict: changes needed

## Findings

**MEDIUM** — `~/.claude/foreman/plugin/lib/fmhooks.py:361-373` (`_use_plugin_grant`) and `:341-358` (`_pin_problem`) — Race between two sessions: `_pin_problem` reads `act.meta["plugin_pin"]` from an in-memory `Brief` loaded **without** the project lock (`_guard_ctx` in `fmhooks.py:478-498`, called before any `c.lock`). If a concurrent session's `_grant` (fmhooks.py:539, called from `_resolve_approvals`/`_grant_prompted` under the project lock) replaces the pin for a *different* plugin B in the window between that unlocked read and `_use_plugin_grant`'s locked re-read, `_use_plugin_grant` only checks `"plugin" in b.meta["allow"]` (fmhooks.py:366) — it does not re-verify the pin still names the plugin that was actually validated. It then unconditionally does `b.meta.pop("plugin_pin", None)` (line 369), silently burning the fresh yes for B while logging `"plugin grant used for: [plugin A]"` (line 370). The user's just-granted approval for B is lost with no error, and B is never installed. **Fix**: re-run `_pin_problem` (or at minimum compare `plugin_pin[0]` to the validated target) inside `_use_plugin_grant`'s locked section before popping. Confidence: high (verified by reading both functions; no lock covers the gap, no test covers the race).

**MEDIUM** — `~/.claude/foreman/plugin/lib/fmhooks.py:539-549` (`_grant`) — If `fmplugins.content_hash(pin)` returns `None` at grant time (e.g. the plugin was uninstalled, or its marketplace entry vanished, between `fm ask --pin` and the user's yes), the code pops any old pin and grants `"plugin"` into `b.meta["allow"]` anyway, but never sets `plugin_pin` (the `if h:` guard at line 547 skips it). Every subsequent install/enable then gets blocked by `_pin_problem` (`len(pin) != 3` at `fmhooks.py:351`) demanding a re-ask — but because only install/enable computes a `[plugin X]` target (`fmguard.py:140-144`), the now-unscoped `"plugin"` grant remains fully spendable by an unrelated `claude plugin disable`/`fm plugins add-marketplace` call via the ordinary `_use_plugin_grant` path, which the user never asked to authorize. **Fix**: when a pin was requested but `content_hash` fails at grant time, don't grant `"plugin"` at all — log/deny and require a fresh ask. Confidence: medium (verified via code reading; not covered by any test).

**LOW** — `~/.claude/foreman/plugin/lib/fmhooks.py:351` — `_pin_problem` assumes `plugin_pin` is always a well-formed 3-element list. A hand-edited or malformed brief (per the audit's stated threat: "a hand-edited or malformed `plugin_pin` line") such as `plugin_pin: [a@m, hash]` (2 elements, `pin[0]` already equal to `target`) still trips `len(pin) != 3` and prints "names a@m, not a@m" — a wrong but still fail-closed message. A bare scalar value (`plugin_pin: yes`, parsed by `fmcore._parse_value` at `fmcore.py:512-518` as a plain string since it isn't bracketed) makes `pin[0]` index the string's first character rather than erroring cleanly. Behavior is safe (always denies) but diagnostics are misleading. **Fix**: `isinstance(pin, list) and len(pin) == 3` before indexing, with a clearer "brief meta is corrupt" message. Confidence: high (verified `_parse_value` and `_pin_problem` directly).

**LOW/perf** — `~/.claude/foreman/plugin/lib/fmplugins.py:116-143` (`_tree_hash`/`content_hash`) — Full synchronous SHA-256 of every file's entire content, with no size cap or caching, runs on the fail-closed `PreToolUse` guard path (`_pin_problem` → `content_hash`, `fmhooks.py:355-357`) on every plugin install/enable attempt (and again in `fmcli.cmd_ask` and again in `_grant`). For a large plugin this adds real latency to a hot hook path (this repo benchmarks hook budgets at 150ms p95 via `plugin/tests/bench_hooks.py:19`). Separately, `elif os.path.isfile(path): with open(path, "rb") as fh:` (lines 127-129) has no `try/except`; an unreadable file inside an installed plugin's tree raises, which is only caught by `_pre_tool_use`'s outer catch-all (`fmhooks.py:432-437`), fail-closed but with a generic "internal error" message rather than naming the offending file. **Fix**: catch `OSError` per file (skip/hash a sentinel), and consider caching `content_hash` per plugin path+mtime. Confidence: high (code read directly); severity is judgment (fails closed either way, so not a correctness bug, but a latency/diagnostics gap).
