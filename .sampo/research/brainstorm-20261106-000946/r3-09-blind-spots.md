# Brainstorm — lens: blind spots

- **Census the user's own typed verbs before designing any decider slot** — FEATURE — value 5 — effort M — risk low — category: blind-spot
  Why: T-3312 (Kalevala depth), T-3316 (Headroom census), T-3321 (Fleet claims), T-3339 (Landscape scan), T-3340 (Benchmark queue fixture), T-3342 (mirror rename), T-3352 (hook latency), T-3353 (lessons into prompts) are all asks the user had to make that no earlier brainstorm predicted. The common shape: the user names a *boundary* or *census* capability (what is the complete set of X?) that the tower had never enumerated. Question a brainstorm should have asked: "What is the complete set of things Sampo has never been asked to do, and what is the maximum this capability can grow to?" The ideas above cover individual boundaries but not the *meta-capability* of discovering them. Done when: `sampo blindspot census` prints a list of user-typed verbs (from the ledger) that no capability map, coverage.md row, or verb table covers, with a count that drops as capabilities are added.

- **Make "what did the user have to type by hand this week?" a first-class, always-on metric** — FEATURE — value 5 — effort S — risk low — category: blind-spot
  Why: T-3353 (tonight's lessons into prompts) and the user's steer "manage all of that across sessions too, like a consensus thing" both point to the user having to *re-teach* Sampo the same thing across sessions and machines. No brainstorm predicted a standing metric for "the user had to say this again." Question: "Which of the user's own habits is Sampo still making the user do by hand, and can we list it without reading any code, only the ledger?" Done when: `sampo doctor` prints "You typed these by hand this week: [list]" with a 14-day trend, sourced from ledger diff between user messages and Sampo's pre-drafted responses.

- **Ask "what does this box know that the other box doesn't?" at every capability addition** — FEATURE — value 4 — effort M — risk low — category: blind-spot
  Why: T-3321 (Fleet claims on git refs) and the user's steer about "many sessions, one repo, many machines, no duplicates or drift" reveal a boundary the tower never named: the *machine* is a surface with its own knowledge, and Sampo has no census of what differs across machines. No earlier brainstorm predicted a cross-machine knowledge diff. Question: "What does this box know that the other box doesn't, and what should flow between them?" Done when: `sampo fleet diff` prints per-machine deltas in installed model versions, card store contents, standing rules, and lesson confidence, with a "should sync" flag per delta.

- **Give the bench fixture a "what does it *not* cover?" line, permanently** — CLEAN — value 4 — effort S — risk low — category: blind-spot
  Why: T-3340 (Benchmark queue fixture) was an ask the user had to make. The bench exists but no one asked "what scenarios does it leave out?" The standing rule "coverage must be real" applies to coverage.md, not to the bench. Question: "Which scenario classes does the held-out bench leave uncovered, and what would a complete, best-in-class bench include?" Done when: `sampo bench coverage` prints a list of (stack × bug-type × stage) cells with no fixture, and `sampo bench add --cell X` files a task to fill it.

- **Wire hook latency to a named budget, not just a bench bar** — FEATURE — value 4 — effort S — risk low — category: blind-spot
  Why: T-3352 (Measure the hook handler) and the user's steer "Sampo's work shouldn't eat the whole CPU" both point to hook cost being a *budget* the user sets, not a number the tower measures in isolation. No brainstorm predicted "the hook is eating the user's CPU budget." Question: "What is the hook's allowed share of the host's turn, and what happens when it exceeds it?" Done when: `sampo doctor` shows "Hook budget: 50ms (p99: 32ms)" and a "degraded" flag when p99 exceeds the budget, with a command to raise or lower it.

- **Treat Sampo's own prompts as an external surface with its own injection scan** — SECURITY — value 5 — effort M — risk med — category: blind-spot
  Why: The user's steers about "keep data on the owner's hardware" and "nothing sent without an explicit setting" apply to *external* sends, but the tower's own injected text (MASTER.md, skills, hook notes) is a surface the user *receives* and no brainstorm treated it as one. T-3353 (tonight's lessons into prompts) makes this worse: the prompt is now a *channel* the user doesn't fully control. Question: "What is in the injected text that the user did not approve, and what would break if a malicious line were planted there?" Done when: `sampo inject audit` prints every injected line with its source, approval status, and a "planted-line" canary test result.

- **Wild — Run a "Sampo is gone" weekly drill and log what the user had to do by hand** — FEATURE — value 5 — effort M — risk low — category: blind-spot
  Why: No brainstorm predicted a *negative* census: what the user *needs* Sampo to do that Sampo is not doing, measured by removing Sampo. The user's steer "I don't want to just cap the cost of things to prevent the work from getting done, I want it to still get done" implies the user wants to know Sampo's *marginal value* per session, not just its cost. Question: "What did the user have to do by hand in the last 24 hours that Sampo could have done, and what does that cost?" Done when: `sampo ghost week` disables all Sampo capabilities for one live session, logs every user action, and prints "Sampo would have saved: [X minutes, Y asks]" at session close.

- **Wild — Give the *user's silence* a boundary: "what did Sampo say into the silence?"** — FEATURE — value 4 — effort M — risk low — category: blind-spot
  Why: The user's steer "when the user goes quiet for a week, does Sampo know it should be quieter too" and the earlier idea "silence is not consent" both point to silence as a *surface* Sampo writes into, not just reads from. No brainstorm predicted a census of "what Sampo said into the silence." Question: "What did Sampo do, send, or decide during the user's silence, and was any of it unwanted?" Done when: `sampo silence audit --since <time>` prints every Sampo action (commits, pushes, drafts, model calls) during a user-quiet period, with an "unwanted?" flag per action.

- **Name the "what does the user's *other tool* do that Sampo should not?" boundary** — FEATURE — value 3 — effort S — risk low — category: blind-spot
  Why: T-3339 (Landscape scan) asks about the *field* but not about the user's *other tools*. The user has Claude Code, Codex, Gemini CLI, opencode — Sampo is a discipline *layer* over them, but no brainstorm asked "what does Claude Code do natively that Sampo is duplicating, and what should Sampo stop doing?" Question: "Which of Sampo's capabilities overlap with the host's native features, and which should Sampo retire?" Done when: `sampo native parity` prints per-verb a "host-native?" flag and a "retire-when" date, sourced from the landscape scan.

  Why: The eight "missed asks" (T-3312 through T-3353) all share a shape: the user names a *census* or *boundary* the tower had never enumerated. Done when: `sampo blindspot next` prints the top 5 unasked capabilities, ranked by (user frequency of adjacent asks × cost of not having them), updated every Rune generation.
