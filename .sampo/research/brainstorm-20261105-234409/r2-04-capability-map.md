# Brainstorm — lens: capability map

- **Publish a full decider capability map in the pack's own grid format** — FEATURE — value 5 — effort M — risk low — category: docs/capability
  Why: The pack defines coverage as a 13-capability × surface × stage grid (standing rule: coverage by grid, "no empty cells" ends the run). The decider request names five dimensions (what it does, trained on, trained/served, measured, improves Rune) but nothing yet maps each to a capability row, surface or stage; the lens "capability map" exists precisely to list every capability a best-in-class version has and propose the ones the pack doesn't show. Done when: `sampo decider map` prints rows (decide, verify, route, abstain, distil, serve, measure, retrain, generalise) × surfaces (cli, web UI, drive, hooks, phone) × stages (plan, act, close, resume), each cell holding a named slot or a recorded n/a, and `sampo doctor` flags an empty cell.

- **Define the model-slot registry as the single source of truth** — FEATURE — value 5 — effort M — risk low — category: capability
  Why: The user asked "how it is served on this box" and "how it improves every Rune generation"; earlier brainstorms scattered slots (decider, close-verifier, loop-predictor, Ward head) across ideas with no registry. A capability map needs one object listing every slot, its model, its abstain contract, its free-arm baseline, and its adoption gate. Done when: `sampo slot list` shows each slot with model id, endpoint, abstain-rate, holdout score, and a one-command adopt/rollback, and no session path references a model not in the registry.

- **Define the fail-safe and degradation capability set** — FEATURE — value 4 — effort M — risk low — category: capability/security

- **wild: Build the decider as a living organism with a metabolism, immune system and fossil record** — FEATURE — value 3 — effort L — risk high — category: capability/wild
  Why: The standing rule says no idea is killed for ambition; the ecosystem metaphors recur in the pack. A wild capability map treats the decider as an organism: its "metabolism" is the token cost per decision, its "immune system" is the Ward classifier that rejects poisoned training rows, its "fossil record" is the sealed museum model that never trains, and its "reproduction" is the per-project adapter that forks from the base. This reframes the entire capability set as biological functions with measurable health indicators. Done when: `sampo decider vitals` prints metabolism (tokens/decision), immune status (poisoned rows detected), fossil integrity (museum model hash), and reproduction (adapter count per project), and a drop in any metric files a task.

- **wild: Let the decider write its own capability map and defend it against a hostile reviewer** — FEATURE — value 3 — effort L — risk high — category: capability/wild
  Why: The standing rule says the tower advances itself. A wild capability: the decider generates its own capability map from the ledger, then a cold child on a stronger model reviews it and files gaps. The map is never hand-written; it is an artefact the model produces and is accountable for. This makes the capability map a live, self-verified document rather than a static checklist. Done when: `sampo decider map --regenerate` produces a map, a cold child reviews it within 5 minutes, and any gap the child finds becomes an open task with the child's quoted evidence.

- **wild: Publish the decider's capability map as a public "Sampo discipline" spec that any harness can implement** — FEATURE — value 4 — effort M — risk med — category: capability/wild
  Why: The user's standing rule says Sampo is not specific to Claude Code; the discipline layer should be portable. A wild capability: the capability map is not just an internal checklist but a public, versioned spec (like a protocol) that any agent harness can implement, with a conformance test suite. This turns the decider from a Sampo feature into a field contribution. Done when: `sampo decider spec --version N` emits a machine-readable spec, a conformance suite runs against it, and the spec is published on the site with a version history and a "what changed" diff.

- **Add a per-project consent and data-minimisation capability** — FEATURE — value 4 — effort S — risk low — category: capability/privacy
  Why: "Keep data on the owner's hardware, local engines, nothing sent without an explicit setting" is the privacy lens. The decider must have a named capability for: per-project opt-in/out of training, a minimum-data threshold below which the model abstains, and a provenance flag per row (user-authored vs tool-authored vs model-authored). The pack mentions consent flags but not as a decider capability with a check. Done when: `sampo decider consent` shows per-project status, the minimum-brief threshold, and the provenance distribution, and `sampo doctor` fails if a project is in training without consent.

- **Map the "how it improves every Rune generation" as a causal loop with a measurable delta** — FEATURE — value 5 — effort M — risk med — category: capability
  Why: The request explicitly asks how the decider improves Rune generations. A complete capability: every Rune generation has a before/after scorecard, the delta is attributed to the decider's adoption (not to other changes), and the attribution is verified by a counterfactual arm (same Rune with the decider off). Without this, "improves every Rune" is an unverified claim. Done when: `sampo decider delta --rune N` shows the before/after scorecard, the counterfactual arm result, and the attributed delta, and a Rune with no measurable delta is flagged.
