- Time travel (T-0898): `sampo at TARGET -- CMD` runs CMD in a throwaway worktree of a task's start snapshot (uncommitted work included) or any commit, branch or tag (`fmcli._run_at`, as `sampo bisect` and `sampo task prove` use), prints the result and exits with CMD's code; the working tree is never touched. The guard reads the command inside `sampo at` and `sampo quiet` as if typed (`fmguard._fm_trailing`).
- Shell (T-0917, T-0924): bare `sampo` in a project prints the status line and `sampo next` (help elsewhere); `sampo complete -- WORDS` prints what can come next from the live argparse tree (verbs, a verb's subcommands, options) and open task ids where a positional goes; `sampo complete --shell bash|zsh` prints the hook to `eval` in the shell's rc.
- Plugin workflows (T-0787, `plugin/workflows/*.js`, run as `/foreman:<meta.name>`): `review` (a general-purpose scope agent writes the diff for a range, branch, task id or the uncommitted change to a mktemp folder; one `foreman:fm-reviewer` per lens; two skeptics per finding, dropped only when both refute; returns confirmed findings and `sampo task finding` lines) and `ideas` (one Explore agent per lens reads the code and marks each idea new/partial/exists with file:line evidence; dedup by title words against `seen`; a critic names up to 4 missing angles for up to 2 more rounds; returns the catalogue and an intake block). `test_workflows` checks each file: a pure-literal meta first, name = file name, phase titles declared, no Date.now/Math.random/new Date(), and `node --check` of the body wrapped as the runner runs it.
- MCP server (T-0245, `fmmcp.py`): `sampo mcp` speaks MCP over stdio (JSON-RPC 2.0, one message a line, stdlib only) for the project it starts in: `initialize`, `ping`, `tools/list`, `tools/call`; notifications get no answer; a malformed line is a -32700 error, an unknown method -32601, any other failure -32603 — and the server keeps serving. Tools, all read-only, each running the matching sampo command so the CLI stays the one implementation: `state`, `next`, `recall {query}`, `research_list`, `research_read {name}` (a plain note name, no paths, no symlink out of the folder), `task_show {id}` (T-NNNN only), `checks` (the last `sampo check` run from the ledger); a recall query can't start with `-` (never a flag), and a line over 1 MB is refused without being held. Everything sent is redacted; a sensitive project lists no tools and refuses calls. Registering it — `claude mcp add foreman -- sampo mcp` — is the user's step (the guard's plugin category). T-2172: `exam_scorecard` runs `sampo louhi scorecard` (exit 1, not every capability passing, is an answer); T-2201: `genesis_status` runs `sampo rune status` (the tower's generation, files, coverage, next action and last exam result), so Desktop and other agents see where Genesis stands.
  T-0946: also `lib_suggest`, `lib_search {query}`, `lib_show {name, section?}` and the instruments `outline {path}`, `impact {path}`, `why {target}`, `sym`, `logs`, `data`, `trace` (their input schemas from `fminstr.TOOLS`, each value capped) and `fail {text}` (the text piped in); every path, links followed, must resolve under the project root; no value starts with `-` or holds a NUL; a call with keys outside its schema is refused; each call times out after `FOREMAN_MCP_TIMEOUT` s (default 120) and gets an empty stdin, never the server's stream. `sampo mcp new NAME --wrap 'CMD' [--sub a,b] [--dir DIR] [--force]` fills `plugin/templates/mcp-server/` (server.py, test_server.py: stdlib only, argv only, args matching `[^\x00-][^\x00]*` up to 200 chars, `sub` an enum, a 30 s timeout, a 100 kB output cap) into an empty folder; it refuses shell syntax in CMD, `_NEVER` commands (rm, dd, sudo, shells, xargs, env…), git subcommands outside a read-only list, a bare dispatcher (git, npm, docker…) without `--sub`, and anything `fmguard.check_bash` flags. `sampo mcp register claude [DIR]` prints the `claude mcp add` line; codex and gemini get no line until their format is confirmed against current docs (`sampo agents install` already wires Sampo's own server there).

A sensitive project's export keeps kinds and timings, no words. `sampo desk [--out FILE] [--size WxH] [--every S]` (T-1615: `desk_svg`, `desk_html`, `_desk_write`) draws the glance as a black-and-white card (800x480 by default, scaled) for an e-paper panel or an old phone: SVG, .png through rsvg-convert, or .html that reloads itself, written whole, once or every S seconds (10 or more) into a synced folder; no port is opened. The site's charts (`site/build.py` hbars and pairs `grow-x`, columns `grow-y`, line `draw` with `pathLength="1"`) draw once when seen: `site.js` arms them after its reduced-motion check, `style.css` moves them only under prefers-reduced-motion: no-preference.
  `sampo glance` prints one ASCII JSON line (v, project, task, step, counts, paused, drive, autonomy, and waybar's text/tooltip/class); outside a project it prints `"project": null` and creates nothing. `sampo lsp` is an LSP stub over stdio (Content-Length frames, a frame over 32 MB ends it): initialize, shutdown, exit (code 0 only after shutdown), full sync; didOpen/didChange/didSave(text)/didClose publish the document's proof gaps: a criterion with no verify command (warning) or no `(ac N)` evidence (info, warning once ticked), a step with no evidence (info, warning once ticked). - State location: `state/`, unless `~/.claude` is read-only (Bash sandbox, `claude plugin eval`, a container): then state moves once to `$XDG_STATE_HOME/foreman` (or `/tmp/foreman-state-<uid>`, cleared at reboot) and a marker there keeps every process following it. `sampo doctor` warns while it's in use; `sampo doctor --restore-state` moves it back once `state/` is writable. The guard treats every fallback location as state, and a marker in a directory other users can write is ignored.
- Commands: `sampo help` (or bare `sampo`) lists every command once, in tiers with the everyday ones first (each command's `add(..., tier=(title, order))` registration fills `HELP_TIERS`, T-1144; a command without a tier fails to register); `sampo <command> -h` gives its options. T-1519: `sampo help WORDS` answers "can Sampo do X?" from that same help (`fmrecall.can`: the commands whose name, help and options' help hold at least half the question's non-asking words, rarest first, a command the question names lifted; each line ≤ 100 columns, a long help cut to the clause holding the question's words (`fmrecall.gist`); exit 1 with a plain no when none do; `--all` with words, or a question of only asking words, is refused saying so). T-1699: `sampo which TASK` (`fmwhich`) ranks the skills (`plugin/skills/*/SKILL.md` names and descriptions, read at run time; a user-only one listed as "you type /foreman:X"), the playbooks' headers (title and Use-when lines, 600 characters) and the commands' help (less Sampo's own release tools) against the task's words (`fmrecall.words`: idf, a word in the name weighs triple), and prints each fit with the call that loads it; fits holding under half the task's words together are "Nothing matches" (exit 1). The fence below is runnable: `sampo release-check` (`fmdemo.run_fences`) runs each `bash runnable` fence of README.md and MASTER.md as `bash -e` through `sampo check playbooks`' runner, with HOME, Sampo's home and state and TMPDIR in its own temporary folder, this checkout's `sampo` first on PATH, a `claude` that only fails, stdin closed, its limits, a 120 s timeout and a process-group kill. - State in the repo (opt-in): `sampo sync on` mirrors the project's briefs (archive included), decisions and research into `.foreman/` in the repo, kept current on every sampo change, to commit with the work; git is the transport and the conflict detector: sampo keeps a hash of what it last wrote to or took from each mirror file, so a file changed by a pull or merge is left alone by exports and taken in by the next sampo command, the next session start (a fresh clone turns syncing on unless sync was switched off there) or `sampo sync import`. When both sides changed, the local copy wins and theirs goes to `sync-conflicts/`; files with unresolved merge markers wait for git. The ledger, meta, sessions, pending asks, gates and views stay local; brief logs carry the history. Nothing from the mirror counts for this machine's gates: `allow`/`approved` are stripped both ways (a pulled brief keeps the local grants), `[ran]`/`[tree]` marks and audits from elsewhere are neutralized (audits relabelled `imported`), focus is per machine, and symlinks in the mirror are never followed. sampo writes `.foreman/` (hand edits are `state-direct`); its markdown is left out of the worktree id (anything else placed there still counts) and out of checkpoint git summaries; new ids skip ids the mirror already has. Exports pass through the secret redactor and imports skip files over 1 MB. `sampo sync on` warns when git ignores `.foreman/` (snapshots and task commits then leave it out: `mirror_ignored`) and fails cleanly (sync stays off) when it can't write it. `sampo sync status` shows incoming, repo-only and local-only briefs and, when on, the line a teammate runs to join (`sampo sync on`, T-0962); `sampo sync off [--remove]`.
- Plugins: `sampo plugins find <need>` searches the local marketplace indexes (installed/enabled state, always-on estimate; T-1396: a bad entry is skipped with its reason, and a plugin the marketplace's `renames` points at, or whose name, source or sha changed since `sampo plugins install`, reads as untrusted, keyed in state/plugin-trust.json); `sampo plugins check [ID]` flags enabled plugins with a synchronous Stop hook (competes with Sampo's gate and drive), duplicate MCP servers, or process skills that duplicate Sampo (`sampo doctor` warns); `sampo plugins install ID` (after your yes to `sampo ask TASK plugin --pin ID`; one yes covers one change, and a command bundling several is refused; the yes to install or enable is pinned to that plugin and a hash of its content at the time — the installed copy, else the marketplace entry plus its local copy — so installing another plugin, changed content or a yes over 24 h old is refused with the sampo ask to run again; the newest plugin yes on a task replaces an earlier pin; `setup-plugins.sh`, whose installs the guard can't see, refuses a real run inside a Claude Code session, `--dry-run` aside) installs or re-enables it, and a fresh install is recorded so `sampo uninstall-user` removes it (only once it really landed in `installed_plugins.json`). Nothing found → `sampo plugins add-marketplace <owner/repo | git URL | path>` (same yes), recorded and removed the same way; `sampo plugins forget ID` keeps something through uninstall. `check` also reports the curated conflicts (`KNOWN_CONFLICTS`, the same list `setup-plugins.sh` warns about) and resolves enabled plugins with this project's `.claude/settings*.json`.
- Driven by another tool (T-0077): a session started with `FOREMAN_QUIET=1` in its environment (an orchestrator launching `claude`) gets no Sampo context, nudges, drive or brief requirement; only the PreToolUse guard runs, and blocks what it always blocks. No settings change or plugin disable is needed.

- Compact output (T-0783, opt-in): `sampo compact-output on` adds a PostToolUse Bash hook to `~/.claude/settings.json` (backed up; `off` and `sampo uninstall-user` remove it; new sessions pick it up) that runs `plugin/hooks/compact`, a stdlib-only script: a Bash output over 6,000 characters reaches the model as its first 40 lines, every other line that reads as a failure (exact duplicates once, at most 40, long lines clipped around the failure word), its last 60 lines and the path of the full text under `state/outputs/<session>/`. Measured on 30 days of this machine's transcripts: 1,090 outputs, 10.75M → 6.61M characters (about 1.04M tokens), no distinct failure line lost (exception names like AssertionError count); ~15-19 ms per call. Off, there is no hook at all.
- Oldest-Python gate (T-1805): `sampo check --python VER|oldest` (oldest = `fmpy.NAMES[-1]`, 3.12) finds that interpreter with `fmpy.find((name,), name)` (PATH, ~/.local/bin, uv's; a supported patch only), symlinks it as python3 and python in a temp folder put first on PATH, and runs the usual check; `c.env_id` hashes PATH, so its pass is its own cache entry. Run once before a push to main or a release (the release skill's gate step), not on every sampo check (it would double gate time). A version not found is a usage error.

### Tasks, batches and backlog

- Batches (T-0257): `sampo batch ID ID … [--title T]` builds a host brief (type: the members' most common; tier: S for two S, M for three or more or any M, L if any L; criteria and steps prefixed with each member's id; scope and outside dependencies merged; meta `batch`); members get meta `batched_in` (hidden from `rank_inbox` and `order_queue`), close done-in the host when `sampo task done` closes it, and are handed back if the host is dropped. Started, active or already-batched items are refused.
- Smarter nudges (T-0262): `sampo capture` and `sampo task new` say first when a sampo command's help already covers the request (`fmrecall.covered`: ≥ 3 shared words and ≥ 60% of the help's; the best two, with the drop command). T-1662: `sampo capture` refuses a near-duplicate of an open task of the same type (`fmrecall.near_tasks`: ≥ 60% of the two titles' tokens shared, 2 or more, identifiers like `fmcodetui` or `fmcli.py` kept whole; scopes that never meet, or other names or numbers, are other work), naming it, with exit 5 (`{"refused": "near-duplicate", "of", "title"}` under `--json`) and no brief or attachment written; `--anyway` keeps both. An open task of another type is noted, not refused, and a FEATURE close to done work names that task. Only `sampo capture` checks: `sampo intake`, `sampo task new` and `sampo research --from-agent` don't; `fmfixes._escalate` passes `--anyway` (it dedupes by signature). `sampo decide … --revisit "after YYYY-MM-DD" | "when PATH changes"` tags the decisions.md row (a path trigger keeps the file's content hash); once it fires, `sampo next` carries the decision (and the pane shows it) until a later `sampo decide … --revisited WORDS` or `--reverses WORDS` settles it.
  T-2167: `--check CMD` stores `[check: CMD]` on a rule: only `sampo rune check`, `sampo louhi scorecard` or `python3 plugin/tests/run.py test_…` (`c.check_argv`: shlex, never a shell, refused when written and again when run, since it runs later outside the PreToolUse guard); `--check "pending T-NNNN"` (`c.CHECK_PENDING`) marks a rule whose enforcement a task is still building; `--cites` naming a steer or the user in other words warns. `c.steer_checks(p)` lists each row cited from a user steer (`c.STEER`) and not settled by a later steer-cited row (a session's own `--reverses` can't retire the user's rule) that has no check, a pending one, or, when run, a failing one with its last output line (each command once, `sys.executable`, cwd the repo, 900 s): sampo rune sweep N's steer checks row and sampo doctor's (pending left out). Next's hints (the batch suggestion, installed skills that fit) are counted in the project's `hints.json` where UserPromptSubmit injects them: one shown and not used before the next injection counts as ignored, and past `QUIET_AFTER` (6) it shrinks to its command; running `sampo batch`, calling a skill, or a failing `sampo check` restores it.
- Review risk (T-0885): every `sampo tour` row carries a verdict — review, glance or skim — with its reasons (`fmmap._risk`: a security-sensitive path or added code (`c.sensitive`) +3, runs in CI, on install or brings dependencies +2, over 50/200 changed lines +1/+2, a code file with no test changed beside it +1, deleted code +1, a hot file +1; review at 3+; tests, docs and generated files skim, unless a test file mostly lost lines), and a header naming what to review first (highest score first, 8 named). `sampo tour --since REF` tours everything since REF's merge base with HEAD, uncommitted work included: the morning read of a long unattended run, or a branch before merging (`sampo tour --since main`). Only code files count as "used" in the reading order.
- Handoff (T-0263): `sampo tour ID` lists a task's changed files in reading order — a code file before the code files that name its stem (sampo impact's heuristic; tests are never "used", stems under 4 characters and names like index/utils/types are skipped, cycles fall back to most-used first, docs and data last) — with +/- lines, what each uses and the step being worked at its last edit; a finished task with one commit naming `(ID` is read from that commit. `sampo pr ID` adds the proof: the red→green command, each audit lens's newest verdict, inconclusive runs, the Assumptions with their tags, and the task's bench replays from the newest saved runs. `sampo export agents` writes AGENTS.md for other harnesses (Codex, Cursor, Gemini): how work is done here (with or without fm), the user's last corrections, the project map, recent lessons and decisions, and the playbook index — redacted, under 32 KiB (Codex's default read limit), with a generated-by marker; an AGENTS.md without the marker, a symlink or an unreadable path is kept unless `--force`; playbooks are named by plugin-relative path, and a sensitive project (`sampo sensitive on`) exports no corrections, lessons or decisions. T-1043: `sampo export cursor` writes `.cursor/rules/foreman.mdc` (frontmatter `alwaysApply: true`) and `sampo export gemini` writes GEMINI.md, the same body and the same keep-unless-`--force` rule; every target adds a "Known fixes" section (trusted fixes only, redacted and defanged, at most 15; none in a sensitive project).
- `sampo inbox spec FILE` (T-1165, `fmeco.inbox_spec`): each unchecked `- [ ] text` of a markdown checklist (path from the shell's cwd; fenced blocks and empty items skipped) becomes one inbox brief, source `spec`, its text redacted and defanged behind `| ` (title tagged when instruction-like). A Sampo-owned `CONTEXT: spec <file> item <hash>` line dedupes reruns (item text can't forge it). At most 1 MB and 100 items per run, each limit reported.
- Backlog tools (T-1664, `fmeco`; `/foreman:backlog` asks through AskUserQuestion): `sampo inbox first` (S items waiting on nothing open, with why), `sampo inbox swipe [--apply ID:revive|drop|keep,…]` (the deferred pile, all verdicts checked before any applies), `sampo inbox pick` / `sampo inbox prefer WINNER LOSER` (close pairs; choices kept as title-word weights in the project's prefer.json, `c.title_tilt` adds at most ±2 to rank_inbox's value), `sampo inbox ticket FILE|-` (one brief: type from labels or a traceback, criteria from checkboxes or a criteria list, the first command as a repro step, scope from trace paths inside the repo; text redacted, defanged, quoted, backticks turned to quotes so no verify command rides in). More (T-1866): in a terminal `sampo inbox swipe` asks one item at a time (`swipe_loop`: r revive · k keep · d drop · s skip · q stop, each applied as said; a pipe or `--json` gets the list); the sampo smith app's backlog view (`I`) does the same; `sampo inbox pick` skips items waiting on an open one and with probability `--epsilon P` (default 0.1) pairs an item with a farther one of its kind; `sampo inbox prefer --reset` deletes prefer.json. `fmcli.spike_note`: an L FEATURE's first focus says spike first unless a step spikes, probes or prototypes.

  GitHub too (T-1869; `fetch_gh`, `_gh_json` shared with `sampo inbox gh`): `gh:OWNER/REPO#N`, `#N` or an issue URL runs `gh issue view` in the root, the key canonicalized from the answer's URL, and an issue `sampo inbox gh` captured is that brief (kept as is; `sampo inbox gh` in turn skips a `CONTEXT: ticket github` brief).
