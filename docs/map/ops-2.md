### Hooks, notes and steering

<details>
<summary>notes</summary>

- Steering as data (T-0264): a correction that says never/don't/stop X (UserPromptSubmit) also keeps X's key words in the project's `vetoes.json` (newest 30, one per set of words); PreToolUse adds a note quoting the user when a Bash command, or an edit (its path plus the edit verbs), carries every key word — a note, not a block — and the pane shows the newest one (✋). Each clause is read on its own ("No, I don't think so, never deploy on fridays" keeps deploy/fridays; opinions like "don't think" are skipped), curly apostrophes count, and `sampo vetoes` lists them (`rm N` drops one that no longer holds). A veto that should stop, not note, becomes a user rule (T-0971, hookify's idea): `sampo rule add PATTERN [--on bash|path] [--block|--warn] [--why T]` keeps a Python regex in the project's `rules.json` (compiled at add time, at most `RULE_MAX` 300 characters; `--from-veto N` builds one from veto N's key words, its why the user's words); PreToolUse, after the guard, searches the first `RULE_SCAN` 4,000 characters of a Bash command (`bash`) or an edited file's absolute path (`path`), all rules within `RULE_BUDGET` 0.25 s (SIGALRM; a rule it couldn't finish refuses the call, fail closed): a block denies with the why (in quiet sessions too), a warn is a note. A rule is a text match, not a parse: quoting or a variable gets past one, so the guard's categories stay the safety net. `sampo rule rm N` is the user's: the guard refuses it from Claude as self-authorize.
  The routing tables — stage words and UI words for installed-skill hints, Claude Code's built-in skills per stage, `sampo audit --split`'s review groups — live in `plugin/skills/routing.json` (read by `c.routing()`, which returns `{}` unless `c.routing_problem` finds every table well-shaped: lists of short strings, plain built-in skill names, non-empty review groups); `sampo evolve --target plugin/skills/routing.json` tunes them like any instruction file, and a revision that isn't a JSON object with the same top-level keys is never benched (an ablation writes `{}`).
- Session map (T-0215): SessionStart adds `fmmap.compact` — one ≤ 500-char line from the project's cached `map.json`; a missing or stale map starts a detached `sampo map` for the next session; dropped first when the context exceeds its 2,000-char budget.
- Stale-fact tripwire (T-0113): `sampo resume`, the session-start context and a re-focus name the paths and backticked code names (with an underscore or inner capital) a brief cites that existed where the task started (`task_base`: `git cat-file -e`, `git grep -w`) and are gone now, so a resumed task re-checks its plan; files it means to create never existed there and aren't flagged. Up to 20 paths and 8 names, 10 s per git call.
- Write validators (T-0947): each Write/Edit/MultiEdit/NotebookEdit in a Sampo project is validated by the PostToolUse hook, which runs synchronously for those tools (async for the rest) so it can answer `decision: block` with the problem; Claude, or the subagent that wrote it, must fix the file first. The project's own: `sampo check onwrite GLOB 'CMD {file}'` (meta `onwrite`; GLOB alone removes it, no words lists them; the command passes the guard when stored) runs in the repo root on writes whose repo-relative path matches, at most 5 s each; a failure blocks with its last 8 lines, a timeout only adds a note. Each block is an `enforce` ledger event.
- Session signals (T-0957): a Stop with an active or queued task that nothing kept going (no drive nudge) is an `idle_stop` ledger event, counted over 7 days by sampo doctor's `idle stops` row (-v); a UserPromptSubmit whose `permission_mode` is `plan` holds the drive like a plan-only prompt; each user prompt is a `prompt` ledger event (redacted, at most 2000 chars, with the permission mode; none in a sensitive project); the first SessionStart after Sampo's version changes on this machine (`state/seen-version`) shows that version's top-level CHANGELOG bullets once as a systemMessage (a fresh install records the version silently).
- Close reuse (T-2644): `sampo task finish` reuses a criterion's run when `Brief.passed_here` finds the newest evidence line of that exact command a [ran] pass stamped with the current `worktree_id` tree and `world_here` world (a newer failed run, another tree or world, or a typed line runs it again); the reused line is recorded as such and the close prints `Reused N run(s)…`; sampo check's gates at close are untouched.
- Shadowed names at edit time (T-2630): the sync PostToolUseValidate entry, after the write validators, notes an Edit, MultiEdit or Write of a project .py file whose own new text starts a column-0 def, class or NAME = that `fmcore.redefinitions` (moved from test_redefinitions, T-2553; `skip_decorated` for this note, so @overload and @f.register repeats pass) finds defined twice: the name and both lines, at most five a note with the rest counted, once per name per session; the file is parsed only when the edit's text starts such a name, and not over 2 MB, unparsable or outside the project.
- Outside text (T-0972): the sync PostToolUseValidate entry also matches WebFetch, WebSearch and `mcp__.*`; a result holding instruction-like text (ignore/disregard previous instructions, `<system>` or `<|im_start|>` tags, "you are now in X mode", "new instructions:", a note to the AI, "do not tell the user", curl/wget piped to a shell) gets one zero-token note that it is data, not the user's request, and an `injection_flag` ledger event; the first 200 KB are scanned. Bash output isn't scanned (a sync hook on every Bash call costs latency). A foreground stdin reader nothing feeds (T-1129: `cat` with no file or `-`, `tee`, python with no script, -c or -m, a shell with no script or -c; no pipe, heredoc, here-string or `<`; compound commands skipped) is denied before it runs: the Bash tool's stdin never closes, so it would hang until the timeout. Replayed on 78,307 recorded commands: 224 denied, all self-matches. The store survives compaction; a store error lets the command go on (an ask, never a guard).
