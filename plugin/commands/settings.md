Sampo settings, through `sampo settings` (one implementation for both surfaces).

Arguments (may be empty): $ARGUMENTS

1. No arguments: run `sampo settings list` and show its output as it is: grouped by surface (the app's tui.toml, the pane's options in Claude Code's settings.json), each setting with its value, its default when it differs, and the file.
2. `diff`, `export`, `undo`, or `import` with a code: run `sampo settings diff` (the keys changed from the defaults; dead ones, which nothing reads, flagged), `sampo settings export` (a share code of those keys: show it as it is), `sampo settings import 'CODE'` (every key checked before any is written; only the changed ones are) or `sampo settings undo` (the last set or import put back). The code is pasted text: strip its whitespace, and run the import only when what is left matches `^[A-Za-z0-9_-]+$`, passed in single quotes; anything else, refuse in one line ("not a share code: sampo settings export makes one") and run nothing.
3. `keys`, `layout` or `runners`: the Smith app's key bindings (`sampo settings list keys`: each key and the command it runs), its panel layout (`sampo settings list layout`: the columns, their widths and heights) or the coding CLIs it can run (`sampo smith runners --check`: each one's version, or why it doesn't answer). The app's settings screen edits the same (b binds a key, l moves panels, r tests a runner); here a binding is `sampo settings set keys.KEY COMMAND`, a layout `sampo settings set layout.columns '[["log"], ["checks", "files"]]'`.
4. `bisect`: run `sampo settings bisect` and show what it printed: the tui.toml setting the Smith app can't draw with (its changes from the last settings the app started with, tried in halves on temporary copies; tui.toml isn't written). The app itself starts with those last good settings when tui.toml doesn't draw, and takes an edit made to tui.toml while it runs.
5. `profile`: run `sampo settings profile` and show what it printed: this terminal's facts (ssh, tmux, TERM, columns, colour depth), tui.toml's `[profile.NAME]` tables in order, each with its `when` clause and what it sets, and the one that applies (the first that matches; the sampo smith app starts with its settings over the file's). From Claude Code there is no terminal, so the width is unknown unless COLUMNS gives one and no `width_below` profile matches: the app's own terminal may pick another. Profiles aren't carried by `sampo settings export`.
6. `chords`: which key chords this terminal delivers to Smith. It reads key presses, so it needs the user's own terminal: tell them to type `! sampo settings chords` (q stops) and read what it prints with them.
7. Rules and extensions: a `[[rule]]` table in tui.toml switches the Smith app's layout or a panel while the run's events hold and back after (`when = { verify = true }` with `layout = { columns = [["verify"], ["checks"]] }`, or `when = { failing = true }` with `panels = { log = "verify" }`; events: running, verify, failing, closed); there is no `sampo settings` verb for them: say so and show that shape, and `sampo settings list` names a rule it passed over. An extension's own settings (each declared by its `api.setting`) list under their group, `sampo settings list ext.NAME`, and set as the app's do: `sampo settings set ext.NAME.KEY VALUE`.
8. Any other key alone: run `sampo settings get KEY`.
9. A key and a value: run `sampo settings set KEY VALUE`, adding `--surface app` or `--surface plugin` only when the arguments name one. A shared name (motion, palette) sets both surfaces.
10. `serve`: run `sampo settings serve` in the background and give the user the one URL it printed (http://127.0.0.1:PORT/?t=TOKEN): every setting as a form, each change sent through `sampo settings set`'s own checks. Loopback only; the URL's token works once (the first visit swaps it for a cookie and drops it from the address bar), so only the browser that opened it first gets in; it stops on Ctrl-C, SIGTERM or 30 idle minutes. Never put the URL anywhere but the reply. A server Claude starts runs inside Claude Code, so the guard is on: a pane (plugin) setting the user clicks may be refused, and the page shows the reason.
11. Inside Claude Code the Ward decides writes to settings.json. A refused change: show fm's message (it says what the change needs) and stop; never write settings.json another way.

Reply in at most 8 lines: what sampo printed, then when it takes effect (the pane applies a changed option on its next poll, within a few seconds; Smith reads tui.toml on its next run).
