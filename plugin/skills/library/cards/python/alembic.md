Alembic schema migrations for SQLAlchemy: revisions, autogenerate, online and offline runs, branches.

## Verify
- `alembic upgrade head --sql`: the migrations render as SQL offline (needs no live DB writes).
- `alembic check`: models match the head revision, with no pending autogenerate diff.
- `alembic heads`: exactly one head (more means a merge is needed).
- `alembic upgrade head && alembic downgrade -1 && alembic upgrade head`: the latest revision is reversible on a scratch DB.

## Test first
For a data migration, write the test that fails first: upgrade to the parent, seed, upgrade, assert.
```python
from alembic import command
from alembic.config import Config

def test_backfill_slug(tmp_db_url, seed_users):
    cfg = Config("alembic.ini")
    cfg.set_main_option("sqlalchemy.url", tmp_db_url)
    command.upgrade(cfg, "abc123_prev")
    seed_users(tmp_db_url)
    command.upgrade(cfg, "head")
    assert all(slug_of(tmp_db_url, u) for u in range(3))
```
For schema-only changes, `alembic check` plus a round trip is the failing check.

## Do
- Generate with `alembic revision --autogenerate -m "..."` and then read and edit the file; autogenerate is a draft.
- Set `target_metadata = Base.metadata` in `env.py`, and import all model modules there so they register.
- Set `compare_type=True` (and `compare_server_default=True` if wanted) in `context.configure`.
- Write `downgrade()` for each revision, or state explicitly that it is irreversible.
- Use `op.batch_alter_table` on SQLite for ALTERs it cannot do natively.
- Add a nullable column, backfill, then set `NOT NULL` in a later step on large tables.
- Name constraints with a `MetaData(naming_convention=...)` so migrations can drop them.
- Get the URL from config or env in `env.py`, never hardcoded.

## Avoid
- Trusting autogenerate blindly: it misses renames (emits drop and add, losing data), enum changes and some constraints. Rewrite as `op.alter_column`/`rename_table`.
- Importing app models inside revision files: later model edits break old revisions. Use `sa.table()` or inline SQL in data steps.
- Two heads after merging branches: `alembic upgrade head` errors. Run `alembic merge heads -m "merge"`.
- Editing an applied revision: other databases never see the change. Add a new revision.
- `create_all()` beside Alembic: the version table drifts from the schema.
- Long locking DDL (index on a big Postgres table) in one transaction: use `postgresql_concurrently=True` inside `op.get_context().autocommit_block()`.

## Review
- [ ] One head; revision ids and `down_revision` chain are linear.
- [ ] Autogenerated output was read: renames, defaults, enums and indexes are correct.
- [ ] `downgrade()` works or is declared irreversible.
- [ ] Data steps do not import application models.
- [ ] Large-table changes avoid long exclusive locks.
