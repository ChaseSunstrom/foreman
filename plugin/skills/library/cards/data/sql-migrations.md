Versioned, forward-only schema migrations that are safe on live tables and tested against a real database.

## Verify
- `alembic upgrade head && alembic check`: migrations apply and models match the resulting schema (Alembic).
- `flyway validate`: applied migrations match files by checksum (Flyway).
- `migrate -path migrations -database "$DATABASE_URL" up`: golang-migrate applies pending files.
- `pg_dump --schema-only "$DATABASE_URL" | diff - schema.sql`: schema after migrating equals the committed snapshot.

## Test first
Apply all migrations to an empty database, then assert the target shape and that old rows survive.
```python
def test_adds_status_with_backfill(migrator, db):
    migrator.upgrade("0007")
    db.execute("insert into orders(id) values (1)")
    migrator.upgrade("0008")
    assert db.scalar("select status from orders where id=1") == "new"
```

## Do
- Make each migration small, versioned and immutable once merged; fix mistakes with a new migration.
- Use expand then contract: add nullable column, deploy code that writes both, backfill in batches, then add constraints and drop the old column in a later release.
- Add constraints as `NOT VALID` then validate (Postgres), build indexes `CONCURRENTLY`, and set `lock_timeout` in the migration.
- Keep schema and data migrations separate; run backfills in batches with a commit per batch.
- Include a down migration only if it is tested; otherwise ship roll-forward fixes.
- Run migrations in CI against the production database engine and version, from empty and from the previous release.
- Serialize runs with the tool's lock so two deployers do not apply at once.

## Avoid
- Editing an applied migration: checksum errors or environments that diverge. Add a new one.
- `ADD COLUMN ... NOT NULL` with no default on a big table, or renaming a column in one step: breaks running code. Use expand/contract.
- Autogenerated migrations committed unread: drops and type changes slip in. Review each statement.
- Long `ALTER` holding an exclusive lock: blocks traffic. Use online techniques and lock timeouts.
- Running migrations from app startup on every instance: races and partial deploys. Run once as a release step.
- Testing only on SQLite while shipping Postgres: dialect differences hide failures. Test on the real engine.
- Data fixes mixed into schema migrations that call application models: they break when models change. Use plain SQL.

## Review
- [ ] Migration applies from empty and from the previous release.
- [ ] No long locks: concurrent index, validated constraints, batched backfills.
- [ ] Deploy order works with old and new code running at once.
- [ ] Applied migrations are untouched; the diff is only new files.
- [ ] Rollback or roll-forward plan is stated.
